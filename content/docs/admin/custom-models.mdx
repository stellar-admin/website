By default, a create or edit page edits the resource's entity, and saves it through the resource's data source. When the form doesn't match the entity, give the page its own *form model*. On an EF Core resource, the form model can wrap the entity and add fields of its own. Otherwise, the page needs a *handler* that saves the form model. For example, giving a guide a sign-in needs a password and a confirmation, which the `Guide` entity doesn't store.

## Adding fields the entity doesn't have

On an EF Core resource, a form that needs a few fields the entity doesn't store, such as a reason for the change, can wrap the entity in a form model. StellarAdmin still loads and saves the entity, and the extra fields reach your [form events](/docs/admin/form-events).

The form model has a property that holds the entity, and a property for each extra field. The example below asks for a reason each time someone edits a trip:

```cs
public class EditTripForm
{
    public Trip Trip { get; set; } = null!;

    [Required, StringLength(500)]
    [Display(Name = "Reason for the change")]
    public string Reason { get; set; } = "";
}
```

To use the form model, pass `AllowEdit()` the form model as the type argument, and a lambda that selects the property that holds the entity. Fields under that property are the entity's fields. The example below adds the reason to an audit entry in `OnUpdating`:

```cs
resource.AllowEdit<EditTripForm>(form => form.Trip, edit =>
{
    edit.Fields(fields =>
    {
        fields.Add(form => form.Trip.Title);
        fields.Add(form => form.Trip.BasePrice);
        fields.Add(form => form.Trip.DestinationId);
        fields.Add(form => form.Trip.Tags);
        fields.Add(form => form.Reason);
    });
    edit.Events(events =>
        events.OnUpdating = (context, cancellationToken) =>
        {
            context.Db.Add(new TripChange
            {
                TripId = context.Entity.Id,
                Reason = context.Model.Reason,
                ChangedAt = DateTimeOffset.UtcNow,
            });

            return Task.CompletedTask;
        }
    );
});
```

StellarAdmin copies the entity's fields onto the stored trip as it does for a form that edits the entity, including [foreign keys](/docs/admin/foreign-keys) and [many-to-many](/docs/admin/many-to-many) fields. `Reason` isn't saved, but `OnUpdating` reads it from `context.Model`. In `OnUpdating`, `context.Model.Trip` and `context.Entity` are the same tracked entity.

`AllowCreate()` takes a form model the same way. The property must hold a new entity when StellarAdmin creates the form model, such as `public Trip Trip { get; set; } = new();`. On the edit page, StellarAdmin creates the form model with its parameterless constructor and sets the property to the stored entity.

The labels of the entity's fields come from the entity's properties, so set `[Display]` on the entity, or the field's `Title`. To validate an entity field that you can't add attributes to, implement `IValidatableObject` on the form model, and name the field by its path, such as `Trip.Title`, in the `ValidationResult`.

When the form edits rows in the [index grid](/docs/admin/inline-editing), a column matches the entity's field without the property name, so the `Title` column edits `form.Trip.Title`.

## Using a form model on the create page

To use a form model on the create page, call `AllowCreate()` with the form model and the handler as type arguments. The example below adds a create page that gives a new guide a sign-in:

```cs
resource.AllowCreate<NewGuideForm, NewGuideHandler>(create => create.Fields(fields =>
{
    fields.Add(form => form.FirstName);
    fields.Add(form => form.LastName);
    fields.Add(form => form.Email);
    fields.Add(form => form.Password);
    fields.Add(form => form.ConfirmPassword);
}));
```

The form model has a property for each field, with the attributes that validate it:

```cs
public class NewGuideForm
{
    [Required, Display(Name = "First name")]
    public string FirstName { get; set; } = "";

    [Required, Display(Name = "Last name")]
    public string LastName { get; set; } = "";

    [Required, EmailAddress]
    public string Email { get; set; } = "";

    [Required, DataType(DataType.Password)]
    public string Password { get; set; } = "";

    [Compare(nameof(Password)), DataType(DataType.Password)]
    [Display(Name = "Confirm password")]
    public string ConfirmPassword { get; set; } = "";
}
```

The handler implements `IResourceCreateHandler<T>`. When someone saves the form, StellarAdmin calls the handler's `CreateAsync()` method with the form model. The example below rejects an email address that's already used, and otherwise saves the guide and sets the password:

```cs
using StellarAdmin.Resources;

public class NewGuideHandler(ApplicationDbContext db, GuideAccounts accounts)
    : IResourceCreateHandler<NewGuideForm>
{
    public async Task<ResourceOperationResult> CreateAsync(
        NewGuideForm form, CancellationToken cancellationToken)
    {
        if (await db.Guides.AnyAsync(guide => guide.Email == form.Email, cancellationToken))
            return ResourceOperationResult.ValidationFailed(
                nameof(NewGuideForm.Email), "A guide with this email already exists.");

        var guide = new Guide { FirstName = form.FirstName, LastName = form.LastName, Email = form.Email };
        db.Guides.Add(guide);
        await db.SaveChangesAsync(cancellationToken);
        await accounts.SetPasswordAsync(guide, form.Password, cancellationToken);

        return ResourceOperationResult.Success(guide.Id.ToString());
    }
}
```

StellarAdmin registers the handler as a scoped service, unless you've registered it already, so the handler can take any service in its constructor. The handler replaces only the data source's create. The page's title and labels still come from the resource.

Return the new record's key with `Success(key)`. StellarAdmin can't read the key from a form model, and a [lookup](/docs/admin/foreign-keys#creating-a-record-from-a-lookup) that opens the create page needs the key to select the new record. To reject the form, return [validation errors](/docs/admin/custom-data-sources#returning-validation-errors) the same way a data source does.

StellarAdmin creates the form model with its parameterless constructor. To start it with other values, call [`UseFactory()`](/docs/admin/default-values).

A field with `[DataType(DataType.Password)]` is always empty when the form is displayed, so when the form has errors, people enter the password again.

## Using a form model on the edit page

To use a form model on the edit page, call `AllowEdit()` with the form model and the handler as type arguments:

```cs
resource.AllowEdit<GuideProfileForm, GuideProfileHandler>(edit => edit.Fields(fields =>
{
    fields.Add(form => form.FirstName);
    fields.Add(form => form.LastName);
    fields.Add(form => form.Email);
}));
```

The handler implements `IResourceEditHandler<T>`, which has two methods:

- `FindAsync()` loads the form model for the record with the given key. Return `null` when the record doesn't exist, and StellarAdmin returns a 404.
- `UpdateAsync()` saves the form model to the record with the given key. Return `NotFound()` when the record doesn't exist any more, such as when someone deleted it while the form was open.

When someone saves the form, StellarAdmin calls `FindAsync()` again, applies the posted fields to the form model, and passes it to `UpdateAsync()`. A property that isn't on the form keeps the value `FindAsync()` loaded. The example below loads and saves a guide's name and email address:

```cs
using StellarAdmin.Resources;

public class GuideProfileHandler(ApplicationDbContext db) : IResourceEditHandler<GuideProfileForm>
{
    public async Task<GuideProfileForm?> FindAsync(string id, CancellationToken cancellationToken)
    {
        var guide = await db.Guides.FindAsync([int.Parse(id)], cancellationToken);
        return guide is null
            ? null
            : new GuideProfileForm { FirstName = guide.FirstName, LastName = guide.LastName, Email = guide.Email };
    }

    public async Task<ResourceOperationResult> UpdateAsync(
        string id, GuideProfileForm form, CancellationToken cancellationToken)
    {
        var guide = await db.Guides.FindAsync([int.Parse(id)], cancellationToken);
        if (guide is null)
            return ResourceOperationResult.NotFound();

        guide.FirstName = form.FirstName;
        guide.LastName = form.LastName;
        guide.Email = form.Email;
        await db.SaveChangesAsync(cancellationToken);
        return ResourceOperationResult.Success();
    }
}
```

StellarAdmin passes the record's key to both methods, so the form model doesn't need a key property.

## Running your own code when a record is saved

On an EF Core resource, run your own code when a record is saved, such as sending an email or writing an audit entry, with [form events](/docs/admin/form-events). With a custom data source, do it in a handler.

When the form matches the entity, the handler's form model can be the entity itself, such as `AllowCreate<Booking, BookingHandler>()` with a `BookingHandler` that implements `IResourceCreateHandler<Booking>`.

## Binding a field with your own code

A *field binder* reads a field's value and applies the posted values with your own code, instead of through the property. Use one for a property without a public setter, such as a read-only list, or when the posted values aren't the property's value. EF Core resources already use a field binder for [many-to-many](/docs/admin/many-to-many) fields, so you'll mostly need your own with a [custom data source](/docs/admin/custom-data-sources).

In the example below, `Supplier` has a list of region codes without a setter:

```cs
public class Supplier
{
    public string Code { get; set; } = "";
    public string Name { get; set; } = "";
    public List<string> Regions { get; } = [];
}
```

A field binder inherits from `FieldBinder`. Its `GetValue()` method returns the value the field's editor displays, and its `BindAsync()` method applies the posted values to the model. The example below fills the list from the posted values:

```cs
using StellarAdmin.Resources;

public class RegionsBinder : FieldBinder
{
    public override object? GetValue(FieldBindingContext context) =>
        ((Supplier)context.Model).Regions.ToList();

    public override Task BindAsync(FieldBindingContext context, CancellationToken cancellationToken)
    {
        var regions = ((Supplier)context.Model).Regions;
        regions.Clear();
        regions.AddRange(context.Values.Where(value => !string.IsNullOrEmpty(value))!);
        return Task.CompletedTask;
    }
}
```

To use the binder, call `UseBinder()` on the field's options after StellarAdmin has configured the resource. The example below uses `RegionsBinder` for the `Regions` field on the create and edit pages:

```cs
using StellarAdmin.Resources.Options;

builder.Services.AddOptions<ResourceOptions<Supplier>>().PostConfigure(options =>
{
    var fields = (options.Create?.Fields ?? []).Concat(options.Edit?.Fields ?? []);
    foreach (var field in fields.Where(field => field.FieldName == nameof(Supplier.Regions)))
        field.UseBinder(new RegionsBinder());
});
```

StellarAdmin uses one instance of the binder for every request, so get services from `context.Services`, not from the constructor. To display an error under the field, call `context.AddError()` with the message.
